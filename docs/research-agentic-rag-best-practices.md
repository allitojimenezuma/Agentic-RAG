# Research: Senior-Quality Agentic RAG Best Practices (2025–2026)

## Summary

For an LLM agent that maintains and queries a persistent markdown wiki via tools, the senior-level architecture is: **hybrid retrieval (BM25 + dense embeddings fused with Reciprocal Rank Fusion), structure-aware markdown chunking with contextual enrichment, a fast cross-encoder reranker on the request path, an agentic LangGraph loop with retrieval grading + query rewrite, and citations bound to chunk IDs with post-generation validation.** Retrieval quality is the highest-ROI lever (hybrid + contextualization cuts top-20 retrieval failures by ~49–67%; Anthropic), hallucinated citations are prevented structurally (cite-or-die schemas + validators, not prompt pleading), and cost/latency is controlled by routing cheap models to retrieval/judgment tasks, caching embeddings, and consolidating tools to reduce LLM round trips. For corpora under ~200k tokens — which a maintained wiki of markdown pages may well be — the best practice is to skip vector RAG entirely and load documents directly with prompt caching (Anthropic's explicit guidance).

## Findings

### Angle 1 — Retrieval quality

1. **Hybrid search (BM25 + dense + RRF) is the baseline, not an optimization.** Dense-only retrieval leaves 20–40% of recall on the floor for queries with proper nouns, version numbers, product codes, and exact phrases, because embedding models are never trained on those tokens (e.g., a vector retriever misses the literal string `ERR_NGX_502`). On the WANDS e-commerce benchmark a tuned hybrid setup reaches 0.7497 NDCG vs 0.6983 (BM25) and 0.6953 (vector-only) — a ~7.4% lift. Notion, Perplexity, and Vespa all run hybrid. [TURION.AI](https://turion.ai/blog/hybrid-search-production-bm25-dense-retrieval/), [dreaming.press](https://dreaming.press/posts/2026-06-24-hybrid-search-bm25-vs-dense-vs-rrf.html), [denser.ai](https://denser.ai/blog/hybrid-search-for-rag/), [datarekha](https://datarekha.com/blog/hybrid-search-at-scale/)
2. **Use rank-based fusion (RRF), not score-mixing.** RRF sums `1/(k + rank)` across ranked lists so documents that rank well in *both* retrievers win, which is robust to incomparable score scales between BM25 and cosine similarity. In LangChain this is `EnsembleRetriever` (weighted RRF, constant `c` default 60). Note `MultiQueryRetriever` does a flat deduplicated union — it does *not* use RRF; RAG-Fusion is the variant that adds RRF. [LangChain EnsembleRetriever reference](https://reference.langchain.com/python/langchain-classic/retrievers/ensemble/EnsembleRetriever), [dreaming.press query-transformations](https://dreaming.press/posts/2026-06-23-query-rewriting-vs-hyde-vs-multi-query-rag.html)
3. **Rerank with a cross-encoder on the hot path; escalate to LLM/listwise rerankers only deliberately.** The reranker runs on every query while the user waits, so architecture choice is a latency decision: pointwise cross-encoders (`bge-reranker-v2-m3`, `mxbai-rerank-v2`) score candidates in parallel (~tens of ms, retrieves top-50→top-5); generative LLM rerankers (`Qwen3-Reranker`) top leaderboards but cost >1s/query for a single yes/no; listwise models (`jina-reranker-v3`) rank the candidate set jointly but batch-limited (~64 docs). Reference pipeline: hybrid k=100 → rerank top 5 → 0.96 Recall@5 / 0.87 Precision@5 vs 0.62/0.62 for vector-only k=5. **Only rerank after confirming first-stage recall ≥ 0.80** (reranking cannot resurrect a chunk the retriever never surfaced). [dreaming.press rerankers](https://dreaming.press/posts/llm-reranker-vs-cross-encoder-vs-listwise.html), [thread-transfer](https://thread-transfer.com/blog/2026-06-17-rag-reranking-llm-colbert/), [OrionAI Build](https://orionai.build/blog/rag-that-doesnt-hallucinate-5-tactics/)
4. **For markdown: structure-aware section chunking with header breadcrumbs, not fixed-size or pure semantic chunking.** Fixed-size splitting breaks semantic units (a chunk ending mid-heading loses context: "## Configura…tion Options"). Chunk on heading boundaries, never split code blocks/tables/lists, and attach a header path breadcrumb so every chunk carries document context. Parent-child retrieval (retrieve small chunks, feed the parent section) fixes the too-small-chunk problem. Semantic (LLM-boundary) chunking showed no clear benefit over fixed-size in a NAACL 2025 systematic study — skip it. [chunkana](https://github.com/asukhodko/chunkana), [structchunk](https://github.laiyagushi.com/yzp0111/structchunk), [Solana Garden](https://solana.garden/guides/rag-chunking-strategies-explained/), [NAACL 2025 paper](https://aclanthology.org/2025.findings-naacl.114.pdf)
5. **Chunk vs whole-doc: contextualize chunks, and consider skipping RAG for small corpora.** Anthropic's Contextual Retrieval prepends a 50–100-token LLM-generated context ("This chunk is from an SEC filing on ACME's Q2 2023…") to each chunk before embedding and BM25 indexing: retrieval failure rate drops 35% (contextual embeddings), 49% (embeddings + BM25), 67% with reranking added. Directly relevant to a wiki: **if the corpus is < 200,000 tokens (~500 pages), just load the whole thing into the prompt with prompt caching** (latency >2x better, cost up to 90% lower) — no RAG needed. [Anthropic — Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval)
6. **Pure substring search is a complement, never the primary retriever.** It is brittle to paraphrase, synonyms, and vocabulary mismatch, and it fails silently on semantic questions. But the converse failure (dense misses exact tokens) is why production systems pair them: keep deterministic grep/substring as a tool the agent can use for exact identifiers, with hybrid retrieval as the semantic layer. Anthropic explicitly recommends agents keep lightweight navigation tools (grep/glob-style) alongside precomputed indexes. [Anthropic — Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [dreaming.press hybrid](https://dreaming.press/posts/2026-06-24-hybrid-search-bm25-vs-dense-vs-rrf.html)

### Angle 2 — Agentic patterns

7. **Diagnose the failure before adding query transformations — they are query-side fixes, not index fixes.** Rewriting fixes *incomplete* queries; multi-query/RAG-Fusion fixes *too-narrow* phrasings; HyDE fixes *vocabulary mismatch*; decomposition fixes *multi-hop* questions. Each adds ≥1 LLM call before retrieval, so each trades latency for recall — if chunking or the embedding model is the real problem, query transformation just adds cost on top of a broken index. [dreaming.press](https://dreaming.press/posts/2026-06-23-query-rewriting-vs-hyde-vs-multi-query-rag.html), [Alex Chernysh](https://alexchernysh.com/blog/query-transformation-for-rag)
8. **The highest-value rewrite for an agent system is conversational contextualization** — resolving pronouns/antecedents against history before retrieval ("how much is that one?" → "how much is the Pro plan per month?"). This is the Rewrite-Retrieve-Read pattern (Ma et al. 2023, arXiv:2305.14283) and it's the one LangGraph's agentic RAG tutorial implements in its rewrite node. [LangChain — Self-Reflective RAG](https://www.langchain.com/blog/agentic-rag-with-langgraph), [agentpatternscatalog — query rewriting](https://www.agentpatternscatalog.org/patterns/query-rewriting/)
9. **Use multi-query (3–5 paraphrases + RRF) for vague/ambiguous queries; be cautious with HyDE on a private wiki.** HyDE (Gao et al. 2022, arXiv:2212.10496) embeds a hypothetical answer, which works on general knowledge but *actively poisons* retrieval on niche internal corpora (your wiki's part numbers, internal terminology) where the generator invents plausible-but-wrong answer shapes. Multi-query/RAG-Fusion (Rackauckas 2024, arXiv:2402.03367) raises recall with bounded risk; RRF-fused multi-query is the production default. [Raudaschl/rag-fusion](https://github.com/raudaschl/rag-fusion), [Jatin Bansal](https://jatinbansal.com/ai-engineering/query-transformations/)
10. **Self-querying retrievers convert natural language into structured filters — high ROI for a wiki with metadata.** `SelfQueryRetriever` lets the LLM emit structured queries (semantic vector + metadata predicates: date, tags, type, author) against declared metadata fields (`metadata_field_info`), improving precision by 25–40% on queries with temporal/categorical/numeric constraints — exactly what wiki queries ("pages updated this month about X") need. Declare metadata fields statically and validate the LLM's filter output against the schema. [thread-transfer self-querying](https://thread-transfer.com/blog/2025-07-30-self-querying-rag/), [LangChain SelfQueryRetriever source](https://github.com/langchain-ai/langchain/blob/c0557cb8addaa78f2d6532d4bb48e07d70221bb4/libs/langchain/langchain_classic/retrievers/self_query/base.py)
11. **Tool-driven retrieval beats single-shot when the query is ambiguous, multi-hop, filter-dependent, or needs follow-up** — and the agentic loop's core value is *retrieval grading + retry*: retrieve → grade relevance (cheap model, binary/structured) → if irrelevant, rewrite and re-retrieve (or fall back to web search per CRAG) → generate only from accepted chunks. This is the self-reflective RAG pattern (Self-RAG arXiv:2310.11511; CRAG arXiv:2401.15884), fully implemented in LangChain's LangGraph cookbooks (`langgraph_self_rag.ipynb`, `langgraph_crag.ipynb`) and the `retrieval-agent-template` (generate-query-or-respond → retriever tool → grade → rewrite loop). [LangChain docs](https://docs.langchain.com/oss/python/langgraph/agentic-rag), [langchain-ai/retrieval-agent-template](https://github.com/langchain-ai/retrieval-agent-template)
12. **Minimize round trips: route-to-retrieve, parallel tool calls, and consolidated tools.** Only invoke the retriever when the agent decides it's needed (decision node, not unconditional pipeline). The LangChain Self-RAG implementation deliberately simplifies the paper: one generation graded against the documents instead of per-chunk generation + double grading — cutting LLM calls and latency while keeping the guardrails. Anthropic's tool guidance: consolidate chained operations into single tools (`search_logs` returning relevant lines + context, not `read_logs`), return token-efficient responses (Claude Code caps tool output at 25k tokens), and make errors actionable prose rather than codes. Agents run a serial LLM-tool loop, so *every* tool call costs a 1–3s round trip — each consolidated tool deletes one. [LangChain — Self-Reflective RAG](https://www.langchain.com/blog/agentic-rag-with-langgraph), [Anthropic — Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents), [CallSphere](https://callsphere.ai/blog/optimizing-agent-tool-calls-reducing-round-trips-api-latency)
13. **For wiki maintenance specifically, adopt the "just-in-time context" + hybrid pattern.** Anthropic's guidance for agents that operate over a file system: load a small up-front context (like `CLAUDE.md`), then keep lightweight identifiers (file paths, headers) and load full content on demand via tools — progressive disclosure, stale-index-safe, and it mirrors how Claude Code works. This is the pattern Karpathy's LLM Wiki (gist) codified for exactly this use case: an agent reads/interlinks markdown pages directly instead of embedding-retrieving every turn; for small wikis, direct file reads beat RAG. [Anthropic — Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents), [Karpathy LLM Wiki](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f), [mindstudio wiki-vs-RAG](https://www.mindstudio.ai/blog/llm-wiki-vs-rag-knowledge-base)

### Angle 3 — Grounding & citations

14. **Free-form citations are hallucinated by default — the binding must be created by the pipeline, not the prompt.** The citation-attribution pattern: assign stable source/chunk IDs at indexing → maintain a registry of IDs *retrieved this turn* → have the model emit claims with `supporting_chunk_ids` (structured) → validate every ID against the registry and refuse/drop unknown ones before delivery. Ask the model to "include citations" and it will fabricate plausible links to documents never retrieved. [agentpatternscatalog — citation-attribution](https://github.com/agentpatternscatalog/patterns/blob/ad774f5fce1844c2816f6ffabe0bf1647d6f9177/patterns/citation-attribution.md)
15. **Cite-or-die schema + verbatim span verification is the concrete tactic with measured results.** Require structured output: `{"answer": ..., "citations": [{"chunk_id": ..., "quoted_span": ...}]}`, then post-verify that `chunk_id` exists in this turn's retrieval and `quoted_span` appears verbatim in the chunk (whitespace-insensitive). Production sequence: naive RAG 18% hallucination → +chunk dedup 14% → +refusal scaffold 9% → +cite-or-die 3% → +rerank-with-recall-gate 2%. Also deduplicate near-identical chunks at index time (MinHash LSH) — duplicated chunks make the model blend facts from near-twin sources into hallucinated statements. [OrionAI Build](https://orionai.build/blog/rag-that-doesnt-hallucinate-5-tactics/)
16. **Refusal scaffolding beats "be careful not to hallucinate."** First-line system-prompt clause: "if the retrieved context does not contain a direct answer, respond exactly with X" — a 5-point absolute hallucination reduction, at the cost of more "I don't know" responses. Explicit refusal + validator is the mechanism; larger models *increase* confidence of false answers rather than fixing grounding. [OrionAI Build](https://orionai.build/blog/rag-that-doesnt-hallucinate-5-tactics/)
17. **Enforce structured output with Pydantic + `with_structured_output` / tool-calling, used for both answers and control flow.** LangGraph's CRAG implementation models binary decisions (relevant/irrelevant) as Pydantic objects bound as tools so conditional edges are reliable; the same mechanism produces the claims/citations schema. Use it for: retrieval grading, query construction (filters), claim+chunk-id output. In long-form outputs watch *attribution drift* — citations degrade as generation length grows (FACTUM, arXiv:2601.05866). [LangChain — Self-Reflective RAG](https://www.langchain.com/blog/agentic-rag-with-langgraph), [HuggingFace structured generation cookbook](https://huggingface.co/learn/cookbook/en/structured_generation), [FACTUM](https://arxiv.org/html/2601.05866v3)
18. **Attribution should reference chunk + page + section, with metadata surviving retrieval.** For a wiki, chunk metadata should include source file path, header breadcrumb, and `updated` date so citations resolve to human-readable locations (Anthropic found resolving opaque IDs to meaningful language reduces hallucination and improves retrieval precision). Reference implementations of the binding: Anthropic Citations API (per-claim citations bound to provided sources), OpenAI Responses API `file_citation` annotations, Dify's automatic citation tracking. [agentpatternscatalog](https://github.com/agentpatternscatalog/patterns/blob/ad774f5fce1844c2816f6ffabe0bf1647d6f9177/patterns/citation-attribution.md), [RedHop](https://www.redhopai.com/guides/rag-citations/)

### Angle 4 — Cost/latency optimization

19. **Route models: cheap model for retrieval-adjacent judgment, strong model for synthesis.** RouteLLM (lm-sys) is a drop-in router that cuts costs up to 85% while keeping ~95% of GPT-4-level performance by sending easy queries to small models; the same principle applies inside a pipeline — Anthropic's contextualization used Claude 3 Haiku, and retrieval grading / filter extraction / relevance judgments are small-model tasks, reserving the frontier model for final grounded synthesis. Cost-aware RAG (CA-RAG, arXiv:2606.02581) extends this to per-query retrieval depth (shallow for definitional queries, deep for analytical ones). [RouteLLM](https://github.com/lm-sys/RouteLLM), [Anthropic — Contextual Retrieval](https://www.anthropic.com/engineering/contextual-retrieval), [CA-RAG](https://arxiv.org/html/2606.02581v1)
20. **Cache embeddings and precompute deterministically.** LangChain's `CacheBackedEmbeddings` wraps any embedder with a hash-keyed byte store; cache document embeddings at index time *and* query embeddings (pass a `query_embedding_store`) since wiki queries repeat heavily. All per-document work (chunking, contextualization, embedding, BM25 index) is one-time precompute — never pay LLM/embedding cost per query for it. Prompt caching on the synthesis step (cache the system prompt + retrieved context prefix) cuts latency >2x and cost up to 90%; RAGCache/TurboRAG push this to precomputed chunk-level KV caches for large-scale serving. [LangChain embeddings docs](https://docs.langchain.com/oss/python/integrations/embeddings), [LangChain CacheBackedEmbeddings](https://reference.langchain.com/python/langchain-classic/embeddings/cache/CacheBackedEmbeddings), [Anthropic prompt caching](https://www.anthropic.com/engineering/contextual-retrieval), [RAGCache](https://chaojin0310.github.io/files/papers/TOCS25-RAGCache.pdf), [TurboRAG](https://aclanthology.org/2025.emnlp-main.334.pdf)
21. **Prefer deterministic computation over LLM calls wherever a rule suffices.** Structured filters (dates, tags, types) should execute as vector-store metadata predicates, not LLM re-reads; deduplication, breadcrumb assembly, and index bookkeeping are deterministic code. A production cost-control layer (semantic caching with ~98.5% hit rate in warmed benchmarks + routing ~81% of traffic to a low-cost model + token-budget circuit breaker) cut LLM cost ~85% without answer-quality loss — but note naive multi-prompting (10 paraphrases of one question) inflated tokens 300% with zero recall/precision gain. [TDS cost-control](https://towardsdatascience.com/rag-is-burning-money-i-built-a-cost-control-layer-to-fix-it/), [OrionAI Build](https://orionai.build/blog/rag-that-doesnt-hallucinate-5-tactics/), [Proximity caching](https://arxiv.org/html/2503.05530v1)
22. **Tool design is the largest controllable latency/cost factor in an agent system.** Anthropic's measured principles: few, well-namespaced tools (prefix namespacing like `wiki_search`, `wiki_read_section`) with clear boundaries beat many overlapping ones; tool descriptions are prompt-engineered (precise descriptions produced state-of-the-art SWE-bench results); responses should support `concise`/`detailed` formats, pagination/truncation with sensible defaults, and actionable error text. Evaluate with tool-use transcripts measuring tool-call counts, token consumption, and error rates — the numbers drive consolidation decisions. [Anthropic — Writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)
23. **Measure before optimizing.** RAGAS (arXiv:2309.15217) gives reference-free faithfulness / answer-relevancy / context-precision metrics; LangSmith traces every retrieval/tool/model step for the same purpose. Eval-gate deployments: an 80-question curated set with ground truth, hallucination-rate regression gate (abort if rate rises >1%), plus production monitors (citation-mismatch rate, refusal frequency). [RAGAS](https://github.com/vibrantlabsai/ragas), [LangChain agentic RAG tutorial](https://docs.langchain.com/oss/python/langgraph/agentic-rag), [OrionAI Build](https://orionai.build/blog/rag-that-doesnt-hallucinate-5-tactics/)

## Gaps

- **No benchmark directly measures "agent-maintained wiki via tools" retrieval quality**; the closest references are Anthropic's context-engineering guidance and Karpathy's LLM Wiki pattern, both qualitative. Suggested next step: build a small eval set of wiki query types (follow-ups, filter queries, exact-identifier queries, multi-hop) and measure hybrid-vs-dense-vs-substring and rerank/no-rerank on the actual corpus.
- **Relative benefit of embedding-based retrieval vs direct markdown reads for a small wiki** is unresolved in the literature; the decision hinges on corpus size (Anthropic's 200k-token threshold) — measure token counts of the wiki and benchmark both paths.
- **Quantitative latency/cost data for tool-consolidation** is anecdotal (Anthropic engineering reports) rather than benchmarked; the acceptance criterion should be measured tool-call counts on real traces.
- **HyDE on private/internal corpora** is flagged as risky (poisons retrieval) but lacks a published controlled study; validate on the wiki before adopting.
