The Wiki Engine — How the Code Manages the Wiki

Everything below the agents is pure Python — zero LLM calls. This page documents the code that reads, writes, searches, matches, indexes, and audits the wiki: how names become slugs, how slugs become paths, how [[links]] are resolved, how index.md is derived, and how health is checked — all deterministically, all testable without a network or a model.

Executive Summary

The Agents → View GitHub Repository ↗
  • The filesystem is the source of truth. Pages on disk + their YAML frontmatter are reality. index.md and lint reports are derived — rebuilt by code, never hand-edited, so they cannot drift from the pages.
  • One canonical model. wiki/model.py parses every page into a Wiki(pages, by_slug) model with sections, resolved links, and word counts. Search, match, index regeneration, and health checks all consume the same model — one parser, one set of semantics.
  • Deterministic by construction. BM25 scores, the create/update/conflict decision tree, index entries, and health findings are all pure functions with stable ordering — unit-testable offline with no mocks.
  • Safety is in the IO layer. Every write is atomic (temp file + rename), slugs are validated against path traversal, and the agents' path-guard middleware can only write inside wiki/.

1. Why not classic RAG?

Classic RAG stores raw documents as chunks in a vector store. Every query pays the same price: embed the question, retrieve the same chunks, and ask the model to re-synthesize an answer from context. Nothing is learned between queries, cross-document contradictions resurface constantly, and there is no notion of "knowledge that has already been processed."

This project takes the opposite stance: the wiki is the artifact. A source is ingested once into structured pages, links, and contradiction flags; queries then read a small, curated, interlinked graph. Synthesis is still per-query, but retrieval and understanding are not — and the code that maintains the wiki is a small, deterministic engine.

DimensionChunk-based RAGWiki-based (this project)
Cost per queryFull retrieval + synthesis over raw chunks, every timeSmall BM25 search over curated pages + navigation
Cross-document synthesisRe-derived from scattered chunks each queryCompiled once into pages and [[links]]
ContradictionsBoth claims surface again and againDetected at ingest, flagged for human resolution
Knowledge over timeFlat — a new source adds more chunks, not more understandingCompounds — pages update, links grow, index is a derived view
Source latencyQueryable immediately, shallowlyIngest is deeper, but the wiki answers better afterward
Failure modeHallucinated citations from irrelevant chunksCite-or-die grounding gate drops any unvisited citation

The agents that drive this engine — ingest, query, lint, fix — are documented separately in documentation.html →. This page stays below the LLM layer: the code that makes the wiki behave like a wiki.

4. Slugs — how names become paths

The slug is the single identity for a page: it is the file path relative to wiki/, minus the .md extension. Names are normalized to slugs by slugify() in io/markdown_parser.py: 

def slugify(name: str) -> str:
    # Normalize unicode to ASCII
    name = unicodedata.normalize("NFKD", name)
    name = name.encode("ascii", "ignore").decode("ascii")
    # Lowercase and replace non-alphanumeric with hyphens
    name = name.lower().strip()
    name = re.sub(r"[^a-z0-9]+", "-", name)
    # Collapse multiple hyphens and strip leading/trailing
    name = re.sub(r"-+", "-", name).strip("-")
    return name

Two concrete transformations:

  • "3D Gaussian Splatting" → 3d-gaussian-splatting
  • "Álvaro Jiménez" → alvaro-jimenez (NFKD strips accents first)

Directory structure mirrors page type

The first path segment of a slug determines the page type. wiki/model.py maps directories to types when frontmatter is missing; create_page applies the inverse mapping when the model submits a bare name:

Page typeDirectoryExample slug
entityentities/entities/mlx
conceptconcepts/concepts/3d-gaussian-splatting
sourcesources/sources/cv
comparisoncomparisons/comparisons/mlx-vs-cuda
overviewwiki rootindex-style root pages

If create_page receives a slug with no / and a type that maps to a directory, it auto-prefixes it (mlx + entity → entities/mlx). Slugs with / are treated as relative paths inside the wiki and are allowed; only path traversal (..) and absolute paths are rejected by _validate_slug.

Reading by slug

_resolve_page_path (in io/wiki_io.py) resolves a slug to a file: the direct path (wiki/<slug>.md) first, then a recursive basename search — so the simple slug mlx finds entities/mlx.md. This is why agents can say wiki_read_page("mlx") instead of the full path.

5. Frontmatter — parse or synthesize

Every page carries YAML frontmatter defined by the pydantic Frontmatter model (schemas/wiki.py): slug, type, title, sources, updated, tags. This is the structured half of the "source of truth" — the search index, match decisions, and health checks all read it. 

---
slug: entities/mlx
type: entity
title: MLX
sources:
- cv.pdf
updated: 2026-07-20
tags:
- ml
- apple
---

parse_frontmatter parses the block with yaml.safe_load and fills sensible defaults for missing optional fields (updated → today, sources / tags → []).

The synthesis fallback — loading never raises

The wiki engine must survive pages the LLM wrote badly. If a page has no frontmatter, or its frontmatter is malformed, load_wiki synthesizes one instead of crashing:

  • type — inferred from the first path segment via _DIR_TO_TYPE (entities/ → entity, …); "unknown" for root pages.
  • title — the first # H1 heading, or the slug basename when there is no H1.
  • updated — the file's mtime (falling back to today).

This is why the health check can flag missing-frontmatter (severity critical) while every downstream tool still works: the model degrades gracefully, the audit reports the real state.

6. The Wiki model

load_wiki(wiki_path) parses the whole directory into one Wiki(pages, by_slug) model (wiki/model.py). Every downstream consumer — search, match, index regeneration, health check — uses this model, so parsing semantics live in exactly one place. 

class Page(BaseModel):
    slug: str
    rel_path: Path
    fm: Frontmatter
    sections: list[Section]   # heading + level + text
    outbound_links: list[str] # resolved [[...]] targets
    word_count: int

class Wiki(BaseModel):
    pages: list[Page]
    by_slug: dict[str, Page]

Note the ordering detail: the complete slug set is built before resolving any [[links]], because link resolution needs the whole namespace. Pages without content produce an empty Wiki rather than an exception.

7. Links — extraction & resolution

Links are Obsidian-style [[Target]] or [[Target|alias]]. extract_links() (io/markdown_parser.py) finds them with one regex: 

_LINK_RE = re.compile(r"\[\[([^\]|]+?)(?:\|([^\]]+?))?\]\]")

Raw [[Target]] text is not a slug — Target is a display name. wiki/model.py:_resolve_link resolves it to an actual page slug in three steps, mirroring the health check's own resolver:

  • Step 1 — the target is already a slug in page_slugs.
  • Step 2 — slugify(target) matches a page's basename or a nested slug ending ([[MLX]] → entities/mlx).
  • Step 3 — unicode-preserving lowercase + hyphens, so accents survive ([[Málaga]] → entities/málaga).

Resolved outbound links drop self-links and unresolvable targets and are deduplicated. wiki_link_graph() (the agent-facing tool in tools/nav.py) uses the same resolution to compute each page's inbound and outbound sets plus an orphan summary — the orphan concept ("no inbound links from other pages") is defined on resolved links, never raw text.

8. Search — BM25 + bounded link expansion

wiki/search.py:search(wiki, query, k=8, types, tags, expand_links=True, depth=1) is the retrieval workhorse. Each page's BM25 "document" is built from title + tags + all section headings + all section texts — tokenized with the same normalization as slugify, so queries and pages speak the same token language.

  • Direct hits — candidates that contain at least one query token, sorted by score desc. Each hit carries a matched_via provenance: title, tags, section:<heading>, or body — plus the headings of the sections that matched, so the agent knows where the query hit.
  • Link expansion — a bounded BFS over resolved outbound_links starting from the direct hits. Expansion hits get a fixed EXPAND_SCORE = 0.1, at most min(2, k) per source page and k in total — never unbounded, always deterministic.
  • Filters — types / tags are predicate filters applied to the candidate set before scoring, so a filtered search never wastes BM25 on excluded pages.

Provenance matters downstream: match_page only counts hits with matched_via != "expand-link" when deciding "similar" vs "conflict" — an expansion hit is a hint, not a match.

9. match_page — the create / update / conflict decision

The heart of ingest is wiki/match.py:match_page(wiki, name, page_type): one pure Python call that decides, before any write, whether a name should update an existing page, create a new one, or be flagged as a contradiction. No score thresholds — the decision rule is structural. 

candidate = slugify(name)
resolved = _resolve_exact_slug(wiki, candidate)   # by_slug key or unique basename
if resolved is not None:
    return MatchResult("exact", [resolved], "exact slug match")

types = [page_type] if _type_dir_exists(wiki, page_type) else None
hits = search(wiki, name, k=5, types=types)
direct = [h for h in hits if h.matched_via != "expand-link"]

if len(direct) == 1:      return MatchResult("similar", ...)
if len(direct) >= 2:      return MatchResult("conflict", ...)
return MatchResult("none", [], ...)
  • exact — slugify(name) is a by_slug key, or the unique basename of a nested slug (mlx → entities/mlx). An ambiguous basename is deliberately not exact — it falls through to search, which surfaces it as a conflict.
  • similar / none / conflict — decided by the number of direct BM25 hits: 1 → update, 0 → create, ≥2 → contradiction.
  • Untyped fallback — when the page type maps to no existing directory (e.g. source on a wiki without sources/), the search runs without the types filter.

The @tool match_page_tool wrapper loads the wiki and returns a one-line decision string the ingest agent branches on: exact: entities/mlx — exact slug match.

10. The derived index

wiki/index.md is not a source of truth. It is a human-readable view rebuilt from the pages. Two modules handle it:

Reading & writing the file — io/index_manager.py

Entries follow two formats, parsed with two regexes:

# Non-source pages:
- [[Display Name]] - summary | Sources: manual | Updated: 2026-08-05
# Source pages:
- [Source Title](sources/subagent-architecture.md) - Ingested: 2026-08-05

read_index splits the file on ## Section headers, maps each section name to a page type (entities → entity, …), and parses entries — including the Source: X/Sources: N field, where a bare number is treated as a count that cannot reconstruct filenames. write_index writes the file atomically (temp + replace), and upsert_entry/remove_entry/ find_in_index provide incremental read-modify-write helpers.

Regenerating — wiki/dedupe_index.py

regenerate_index(wiki_path) rebuilds the whole index from the Wiki model:

  • Lint reports excluded — lint-report-*.md pages are derived artifacts, not content, so they never appear in the index.
  • Summaries — from the first section's body text: wiki links reduced to their alias, markdown links to their text, headings and emphasis stripped, whitespace collapsed, truncated at ~160 characters on a word boundary with a … suffix.
  • Atomic — the write goes through write_index's temp-file + rename, so a crash mid-rebuild never leaves a torn index.

No agent ever calls an "update index" tool — the ingest prompt explicitly forbids it (NEVER call update_index). The index is rebuilt by regenerate_index as a derived view, so it cannot drift from the pages on disk.

11. The log

wiki/log.md is an append-only audit trail managed by io/log_manager.py. Every entry starts with a parseable prefix: 

## [2026-07-26 12:00] update | Fix orphan pages from lint report
- Created entities/python.md to resolve broken index reference C1
- Fixed concepts/machine-learning.md with proper frontmatter
_LOG_PREFIX_RE = re.compile(
    r"^## \[(\d{4}-\d{2}-\d{2} \d{2}:\d{2})\]\s+(\S+)\s+\|\s+(.+)$",
    re.MULTILINE,
)
  • append_log(wiki_path, entry) — appends the header line plus indented detail bullets. Append-only by construction: it never rewrites the file.
  • tail_log(wiki_path, n) — finds entry start positions with the regex, takes the last n, and slices each entry's detail block up to the next entry (or EOF).
  • Operations — ingest, query, lint, create, update, delete are the standard op values.

12. Health check — 7 structural issue kinds

lint/health.py:health_check(wiki_path) audits the wiki with zero LLM calls. It computes seven issue kinds with pinned severities:

KindSeverityDefinitionSuggested action
missing-frontmattercriticalPage doesn't start with --- YAML.Add frontmatter with slug/type/title/updated.
orphanhighNo inbound links from other content pages (resolved links only).Add a [[link]] from a related page.
missing-indexhighPage absent from the regenerated index (checked via full slug, short slug, or title-slug).Add an entry to index.md.
broken-linkhighA raw [[target]] that _resolve_link cannot resolve (lint-report targets excluded).Fix or remove the [[link]].
emptyhighFewer than 50 words of body content.Add substantive content.
missing-relatedmediumNo section whose heading is related (case-insensitive).Add a ## Related section with cross-links.
stalemediumfm.updated more than 90 days before the most recent page's date.Review and update content.

Determinism details that matter:

  • Inbound links come only from content pages' resolved outbound links — and lint-report-* pages are excluded from the audit, from inbound computation, and from orphan detection.
  • Broken links are detected on raw targets (the model's outbound_links are already resolved, so they can't reveal what failed to resolve).
  • Stale is relative: the reference point is the newest page's updated date, not the clock.
  • Issues are sorted by (kind, slug); counts include only kinds that occurred.

The same module renders a deterministic markdown report (_render_report_markdown) with an executive summary, per-severity sections (C1…, H1…, M1…), and a statistics table — used by the lint agent's write_lint_report tool for the no-LLM path.

13. The IO layer — atomic writes & path safety

io/wiki_io.py is the only module that touches page files. Three properties make it safe to hand to an LLM:

Atomic writes

Every write goes through a temp file in the same directory followed by a rename: 

fd, tmp_path = tempfile.mkstemp(dir=page_path.parent, suffix=".md.tmp")
try:
    with open(fd, "w", encoding="utf-8") as f:
        f.write(full_content)
    Path(tmp_path).replace(page_path)
except BaseException:
    Path(tmp_path).unlink(missing_ok=True)
    raise

A crash mid-write leaves either the old file or the new file — never a torn one. The same pattern is used by write_index for index.md.

Slug validation

_validate_slug rejects empty slugs, anything containing .., and absolute paths — while explicitly allowing nested slugs like entities/python.

Page enumeration

list_pages walks rglob("*.md") and excludes index.md and log.md — derived files never masquerade as content.

The agent-side guard (cross-reference)

On top of this, the agents' path_guard_middleware (middleware/guardrails.py) rejects any write-tool argument containing raw/, starting with /, or containing .., and blocks write tools that receive a raw/ source_path. read_source is the only tool exempt — it legitimately reads raw sources. Together: the IO layer makes writes atomic and validated; the middleware makes writes scoped.

14. AGENTS.md — the schema as config

schemas/agents_md.py:load_agents_md(path) reads the schema file and returns its text — falling back to a built-in default matching the spec if the file is missing. It is not parsed: it's a contract written for the LLM, injected verbatim into every agent system prompt (see documentation.html §4).

It defines the conventions the engine's code assumes:

  • Page types → directories: entity, concept, source, comparison, overview.
  • Slug naming — lowercase, hyphens, no special characters (the slugify contract).
  • Links — Obsidian [[Page Name]], a ## Related section on every page.
  • Frontmatter — the exact fields the pydantic model enforces.
  • Update rules & hard rules — the behavioral contract the agents are prompted to follow (flag contradictions, never write outside wiki/, always regenerate index + log).

16. Testability — pure, deterministic, offline

Because every engine function is pure Python, the whole layer runs in milliseconds with no network and no model calls:

  • Pure functions — health_check, match_page, search, regenerate_index, read_index, tail_log, slugify take inputs and return outputs; nothing to mock.
  • Deterministic ordering — search results sort by score with a fixed expansion score, match decisions are structural, index entries follow the pages, health issues sort by (kind, slug). The same input always yields the same output.
  • Graceful degradation — missing frontmatter synthesizes instead of raising; a missing index returns an empty model; a bad slug returns a recoverable error string. The engine is designed to survive the LLM's worst output.
  • Tested through the layers — unit tests cover the IO, parser, index, search, match, and health modules directly; integration tests drive the agents with scripted fake models and assert on real wiki state; the eval layer checks retrieval recall against curated queries on the live wiki.

This is what lets the agents be LLM-flavored without being LLM-dependent: the wiki stays coherent, searchable, and auditable even when the model behaves badly — and the tests prove it.
